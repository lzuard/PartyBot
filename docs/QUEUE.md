# Персональные пулы и очередь — нормативный алгоритм

## Данные и определения

- Catalog: замороженный каталог одной игры.
- Bucket: уникальное значение Points. Пример 20×1, 5×2, 1×6 даёт бакеты [1,2,6].
- Pool[user,bucket]: персональный упорядоченный пул, первоначально все задания бакета в случайном порядке.
- Queue[user]: упорядоченные НЕВЗЯТЫЕ задания. TargetLength = 5, это не максимум.
- Cursor[user]: следующий номинальный бакет в циклическом порядке по возрастанию Points.
- Active: отдельная попытка; в длину Queue не входит.
- Pending: отправленные ответы; ни в Queue, ни в Pool не входят.

Первоначальная случайность применяется внутри каждого пула, порядок сохраняется. Персональные пулы не расходуют пулы других людей. Регистрация идемпотентна.

## Регистрация

1. Создать персональные пулы со случайным порядком.
2. Cursor = минимальный бакет.
3. Вызвать Refill.

## Refill

Пока Queue.Count < 5:

1. От Cursor найти первый непустой пул при циклическом обходе бакетов по возрастанию награды. Каждый бакет проверяется максимум один раз на итерацию.
2. Если непустых пулов нет — закончить; очередь может быть короче пяти.
3. Извлечь первый элемент найденного пула и добавить в хвост Queue.
4. Cursor установить на бакет, следующий ПОСЛЕ ФАКТИЧЕСКИ ВЫБРАННОГО, с циклическим переходом.

Cursor меняется только при успешном обычном добавлении из пула. Возвраты напрямую в Queue и неуспешный поиск не меняют Cursor. Один пустой бакет не останавливает выдачу других. Отдельных квот/минимумов/лимитов по бакетам сверх этого нет.

## Получение

Проверить Open, отсутствие DQ, отсутствие Active и истечение NextTaskAvailableAt. При необходимости Refill. Если Queue пуста — объяснить отсутствие, отдельно упомянуть ожидание модерации при наличии Pending. Не создавать попытку и не запускать кулдаун.

Иначе извлечь голову Queue, создать Active-попытку и вызвать Refill в той же транзакции. Это default: поддерживать пять НЕВЗЯТЫХ сразу после взятия, а не ждать отправки ответа.

## Пропуск

Атомарно: Active → Skipped; удалить кандидат; добавить задание напрямую в хвост Queue; NextTaskAvailableAt = now+N1; затем Refill. Прямой возврат не ограничен длиной и не двигает Cursor.

## Подтверждение

Атомарно: Active → Submitted, новая Pending-заявка; освободить Active; удалить/зафиксировать кандидат; NextTaskAvailableAt = now+N2; Refill. Само задание до решения НЕ возвращать ни в Queue, ни в Pool.

## Approve

Атомарно: Pending → Approved, записать награду и аудит.

- Repeatable=false: задание окончательно исчерпано для пользователя.
- Repeatable=true: вернуть в ХВОСТ ПУЛА СВОЕГО БАКЕТА. НЕ в Queue.

Затем Refill. Поэтому возвращённое в пул задание может попасть в очередь в рамках обычного выбора бакета, если есть свободное место; специального запрета или приоритета нет. Возврат в пул сам Cursor не сдвигает.

## Reject

Атомарно: Pending → Rejected; без награды; добавить задание напрямую в хвост Queue; Refill. Историческую попытку не переиспользовать. Причина и организатор сохраняются.

## Прямые возвраты и размер

Сначала прямой возврат, затем Refill. При Queue.Count>=5 Refill не добавляет из пулов. Повторные прямые возвраты могут дать 6, 7 и больше элементов; это корректно. Получение уменьшает очередь, обычное пополнение возобновляется только при длине <5.

## Инварианты

1. На (Participant, TaskDefinition) максимум одно доступное/незавершённое местоположение: Pool, Queue, Active или Pending. Исторических попыток может быть много.
2. Одноразовое с Approved никогда больше не выдаётся.
3. Повторяемое возвращается в Pool только после Approve; Reject и Skip возвращают прямо в Queue.
4. Не более одного Active на участника.
5. Очередь не пересобирается на /start, показ рейтинга, рестарт или апрув другого задания.
6. Нет фонового random-перевыбора при GetTask; выдаётся голова сохранённой Queue.
7. Возврат и начисление идемпотентны относительно решения.

## Примеры

Пулы A(1)=[a1,a2,a3,…], B(2)=[b1,b2,…], C(6)=[c1]. Начало: Queue=[a1,b1,c1,a2,b2], Cursor=C. После взятия a1, C пуст: добавляется a3 из A; Queue=[b1,c1,a2,b2,a3], Cursor=B.

Если после этого a1 пропущено: Queue=[b1,c1,a2,b2,a3,a1], Cursor=B. Ничего из пула не добавляется. Следующее взятие даёт длину 5 без пополнения. Ещё одно взятие позднее освобождает место и выбор начинается с B.

Если repeatable c1 одобрено и очередь уже имеет 5 элементов: c1 возвращается в Pool[C], очередь не меняется. Позднее попадание c1 определяется Cursor, а не фактом апрува.

Ограничение дизайна: циклические бакеты дают равные возможности в начальной очереди, но возвращаемые задания и разная скорость выполнения не гарантируют равенства потенциальных баллов на протяжении игры. Это ожидаемое поведение, не повод менять алгоритм агентом.
