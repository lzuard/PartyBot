# Эксплуатация и восстановление

Реализовано в этапе 6 (2026-10-20). Команды выполняются из корня репозитория.
Ручная Telegram-репетиция — отдельный этап 7; ниже инструкция, а не отчёт о её прохождении.

## Настройки и подготовка

В Production обязательны BotToken, числовые SuperAdminUserId/OrganizerUserIds,
разные ModerationChatId/ArchiveChatId/AuditChatId, явные N1/N2, абсолютный постоянный
DatabasePath. AuditThreadId необязателен; DisplayTimeZone default Europe/Moscow.
Токен — только secret/environment. Не передавайте его аргументом команды или в логах.
Каталог JSON готовится до первого запуска целевой БД; demonstrationOnly=false для игры.
Позднейшее редактирование JSON не меняет импортированную игру. До Open проверьте
положительные награды, repeatable и окончательные N1/N2.

Суперадмин заранее запускает бота в личке. Бот добавлен в три поверхности с правами
публикации, редактирования своих сообщений и удаления в рабочем чате. Архив приватный,
доступен нужным организаторам, без автоудаления. Проверить тестовую карточку/альбом и
удаление нужно отдельным тестовым ботом; программа не отправляет тестовые сообщения
при старте и не проверяет Telegram-права автоматически.

Не запускайте два polling с одним токеном, в том числе на разных БД. Блокировка
`DATABASE.db.lock` защищает только один путь БД; сам оставшийся файл не означает,
что процесс работает. Не удаляйте lock для обхода активного экземпляра.

## Сборка и запуск

```sh
dotnet restore PartyBot.slnx
dotnet tool restore
dotnet build PartyBot.slnx --no-restore -p:UseSharedCompilation=false
dotnet test PartyBot.slnx --no-restore -p:UseSharedCompilation=false
dotnet publish PartyBot.Api/PartyBot.Api.csproj -c Release --no-restore -o /tmp/partybot-publish
```

Для локального безопасного запуска:

```sh
dotnet run --project PartyBot.Api --launch-profile Bootstrap --no-build -- --Bot:DatabasePath=/tmp/partybot-local.db --Bot:PollingEnabled=false
```

Для production разверните publish-каталог на постоянном сервере с .NET 10 runtime,
передайте настройки окружения и запустите `dotnet PartyBot.Api.dll` из publish-каталога.
Это Generic Host, HTTP-порта/health endpoint нет. Миграции применяются автоматически;
перед обновлением остановите процесс и сделайте backup. `--migrate-only` применяет
миграции без polling/импорта каталога; production-валидация настроек остаётся обязательной.
Не выполняйте EF CLI одновременно с работающим приложением.

## Docker Compose

Есть `PartyBot.Api/Dockerfile`, `deploy/compose.yaml` и безопасный пример окружения.
Docker daemon и Compose нужны на сервере. В текущей среде проверен синтаксис Compose,
но daemon недоступен: контейнерная сборка и deployment не подтверждены.

```sh
cp -n deploy/partybot.env.example deploy/partybot.env
chmod 600 deploy/partybot.env
```

Заполните локальный `partybot.env` (исключён из Git/Docker context): токен, все ID,
реальные N1/N2. Polling включайте только явно `Bot__PollingEnabled=true`, убедившись,
что это единственный процесс для токена. Создайте `/srv/partybot/data` с владельцем
UID/GID 1654 и правами 0700; подготовьте `/srv/partybot/catalog.json`, читаемый этим UID.
Другие пути/UID задаются переменными PARTYBOT_DATA_DIR/PARTYBOT_CATALOG/PARTYBOT_UID/
PARTYBOT_GID. Каталог монтируется read-only, БД — в постоянную host-директорию.
Контейнер работает без root, root filesystem read-only, `/tmp` — tmpfs.

```sh
# Проверка шаблона без чтения файла секретов/раскрытия значений:
docker compose -f deploy/compose.yaml config --no-env-resolution --no-interpolate -q
# Проверка заполненной конфигурации без печати секретов:
docker compose -f deploy/compose.yaml config -q
docker compose -f deploy/compose.yaml build
docker compose -f deploy/compose.yaml up -d --no-build
docker compose -f deploy/compose.yaml ps
docker compose -f deploy/compose.yaml logs --tail 100 partybot
# Остановить перед заменой версии/восстановлением:
docker compose -f deploy/compose.yaml stop partybot
```

Не используйте масштабирование сервиса. Restart policy — on-failure, максимум 3 попытки;
ошибки Telegram 401/409 штатно останавливают приложение, требуют исправления токена/
конфликта polling/webhook и ручного запуска. Бот не удаляет webhook и не сбрасывает updates.
После исправления конфигурации примените `up -d --force-recreate`; перед этим убедитесь,
что прежний процесс остановлен. Логи ограничены 3 файлами по 10 MB. Не публикуйте вывод
`docker inspect` или полной `compose config`: они могут содержать окружение с токеном.

## Диагностика и восстановление доставки

В личном чате суперадмина: `/admin` → «Диагностика» или `/diagnostics`.
Показывает состояние игры, Pending, неполный архив (материалы/карточка), собираемые
кандидаты, незавершённые/Failed доставки, ошибки доски/cleanup и следующий offset.
Страницы ошибок показывают ID/вид, попытки, безопасный код ошибки, retryAt;
содержимое фотоответов, payload и токен не выводятся. Диагностика — состояние БД,
не проверка наличия старых сообщений в Telegram.

- Временные ошибки/429 повторяются автоматически с backoff/retry_after. Не обходите
  ожидание ручным повтором. Текстовый и медиа-шаг ограничены 15 секундами.
- Для Failed сначала исправьте права/настройки, затем `/retry НОМЕР` либо кнопка
  «Повтор #ID» → подтверждение. Отмена и использованные/устаревшие кнопки безопасны.
  Допускается только суперадмин в личном чате; работает и после Finished.
- Повтор сохраняет logical key, число попыток, ошибку, известные message ID, частичные
  копии и отметки удаления. Он не повторяет Approve, не меняет баллы/очередь/snapshot.
  Успешные действия нельзя принудительно проиграть заново. При восстановлении
  WorkMedia пропущенная из-за отказа карточка снова ожидает материалы.
- Неполный архив блокирует cleanup. Сначала восстановите ArchiveMedia/ArchiveCard,
  зависимые ожидающие действия продолжатся автоматически. Частичный copyMessages
  не считается полным; повтор использует file_id, известные частичные рабочие копии
  включаются в cleanup. После сетевого таймаута/сбоя между отправкой и сохранением ID
  возможен дубль; сопоставляйте по Submission/Event ID, exactly-once не обещается.
- При неустранимом отказе удаления оставьте итоговую карточку без кнопок; Failed
  остаётся видимым. Не отмечайте удаление успешным вручную и не удаляйте материалы
  до полного архива. Если редактирование тоже запрещено, исправьте права: логические
  проверки всё равно не позволят старой кнопке изменить терминальное решение.
- Смена настроек chat IDs не перенаправляет уже сохранённые задания доставки: их
  адреса — часть сохранённого состояния. Автоматического переноса архива/доски нет.
- Если бот не отвечает из-за сети/401/409, используйте логи процесса; Telegram-панель
  в этот момент тоже недоступна. Не удаляйте БД, offset или ProcessedUpdates.

Подтверждения повтора и аудит сохраняются транзакционно. После рестарта используются
тот же offset, Active/Pending, порядок очереди, UTC-кулдауны и сроки сборки альбомов.
Debounce не знает ожидаемого общего числа фото: поздняя часть после подтверждения
отклоняется, а не дописывается в сохранённый ответ. Новые части в текущем окне продлевают его.

На 2026-10-20 сверены официальные ограничения: [deleteMessage](https://core.telegram.org/bots/api#deletemessage)
обычно требует возраст сообщения менее 48 часов и нужные права;
[copyMessages](https://core.telegram.org/bots/api#copymessages) сохраняет группировку альбома,
но может пропускать некопируемые элементы. Перед репетицией снова проверьте права.

## SQLite backup и восстановление

На машине с доступом к файлу БД нужен Python 3. Скрипт использует SQLite backup API,
учитывает committed WAL и проверяет integrity_check/foreign_key_check. Он не копирует
просто `.db`, не меняет источник и никогда не перезаписывает существующий destination.
Новые файлы создаются с правами 0600. Backup можно делать при работающем боте;
для обновления/восстановления остановите его. Пути ниже — пример, используйте фактический
DatabasePath и новое имя для каждой копии. Каталог backups заранее создайте с правами 0700.

```sh
python3 scripts/sqlite_backup.py backup /srv/partybot/data/partybot.db /srv/partybot/backups/partybot-before-update.db
python3 scripts/sqlite_backup.py verify /srv/partybot/backups/partybot-before-update.db
python3 scripts/sqlite_backup.py restore /srv/partybot/backups/partybot-before-update.db /srv/partybot/data/partybot-restored.db
```

Порядок восстановления:

1. Остановить единственный процесс. Сохранить отдельную копию текущей повреждённой/
   проблемной БД и технические логи, не уничтожая исходник. SQLite-aware backup
   отклонит нарушение целостности: это не инструмент ремонта повреждённой БД.
2. Восстановить проверенный backup в НОВЫЙ путь. Применить владельца процесса и 0600
   к новому файлу. Для Compose изменить Bot__DatabasePath в `deploy/compose.yaml` на
   `/data/partybot-restored.db`, оставив старую БД нетронутой.
3. Сначала запустить копию с `Bot:PollingEnabled=false` и правильным окружением/
   настройками, проверить старт/миграции. Остановить проверочный процесс.
4. Включить единственный polling с тем же токеном. Проверить `/diagnostics`, состояние
   игры, Pending, кулдауны, итоговый snapshot и возобновление доставок.

Восстановление старого backup теряет изменения после его создания. Telegram мог уже
подтвердить updates новым offset: их повторное получение не гарантируется. Повторная
доставка сохранённого outbox может дать дубли. Предпочитайте рестарт с актуальной БД;
восстановление старой копии — осознанная аварийная процедура, не обычный retry.
Копии содержат персональные данные и file_id; храните ограниченно, отдельно от Git и
с ограниченным доступом. Фото-файлов в backup нет, архив остаётся в Telegram.

## Проверки и репетиция

```sh
python3 -m unittest discover -s scripts -p 'test_*.py' -v
dotnet test PartyBot.slnx --no-restore -p:UseSharedCompilation=false
```

Автотесты проверяют SQLite, рестарт host/offset, повтор update, сборку альбома,
частичные доставки и удаления, retry_after, отказы архива/доски, повторный отказ после
ручного retry, неизменность решения/snapshot, миграции и backup открытой WAL-БД.
Не имитируется гарантированное восстановление неизвестных Telegram ID после обрыва сети.

Перед реальной игрой пройти этап 7 с отдельным ботом и 3–5 аккаунтами: права всех
поверхностей, альбом/замена/Skip/Reject, двойной Approve, DQ, остановка/рестарт,
отказ прав и retry, backup/restore на копии, Close/Finalize/ForceFinalize.
На вечеринке: `/open` → работа → `/close` → разобрать Pending → `/finalize`.
Форс-финал — только с осознанной причиной. Не переносите demo-участников в production.
