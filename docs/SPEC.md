# Продуктовые требования

## 1. Участники

До 70 пользователей. Вход по ссылке и /start в личном чате. Telegram User ID — идентификатор, long/int64. При первом входе пользователь выбирает имя; повторный /start не создаёт новую регистрацию, не пересоздаёт пулы и не сбрасывает прогресс.

Default имени: trim, 1–40 символов, запрет пустой строки и управляющих символов, безопасное экранирование при выводе. Совпадения имён допустимы, отображаются с коротким стабильным номером участника. Смена имени через отдельную команду, без сброса истории, с аудитом.

Бот стилизован под монстра: заранее подготовленные тексты, без LLM. Сообщения об ошибках и времени ожидания понятны независимо от стилизации.

## 2. Роли и поверхности

| Роль | Права |
| --- | --- |
| Участник | Свои задания, ответы, рейтинг |
| Организатор | Одобрение/отклонение заявок, просмотр рабочего чата, архива, журнала |
| Суперадмин | Всё выше, переключение состояний игры, дисквалификация/восстановление |

Списки Telegram ID — в конфигурации, суперадмин один. Telegram-права администратора чата не означают роль в игре.

Поверхности: личный чат участника; рабочий чат модерации; личный чат суперадмина с панелью; приватный архивный канал/чат; отдельный чат или тема бизнес-журнала. Для всех проверяется ожидаемый chat ID. Привилегированные callback проверяют также actor ID.

## 3. Жизненный цикл

Registration: регистрация открыта, игра закрыта.
Open: регистрация, получение, пропуск, отправка ответов и модерация открыты.
Review: регистрация и все игровые изменения участника закрыты, модерация открыта.
Finished: рейтинг зафиксирован, игровые операции и модерация закрыты. Просмотр рейтинга разрешён.

Переходы только вперёд, только суперадмином, с подтверждением. Час 22:00 — организационный ориентир, не cron. Закрытие приёма и закрытие модерации — разные действия.

Обычный финал запрещён при Pending-заявках. Форс-финал требует отдельного подтверждения с числом заявок. Default: остаток становится Unreviewed, без баллов, без возвратов в пулы/очередь; это не Rejected. Итоговый снимок включает причину и факт форса.

После Finished любые изменения рейтинга/дисквалификации запрещены в MVP; исправление итогов — будущий отдельный сценарий, не скрытая возможность старых кнопок.

## 4. Задания

Каталог до открытия: стабильный ID, текст, Points (положительное целое, default 1), Repeatable. Автоматические бакеты по Points. После открытия каталог и награды заморожены. При регистрации — отдельные пулы пользователя, случайный порядок внутри бакетов, начальная очередь. Алгоритм QUEUE.md нормативен.

У участника максимум одно Active-задание и несколько Pending-заявок. После отправки можно продолжить без ожидания апрува. Одно и то же определение задания не может одновременно находиться у пользователя в пуле, очереди, Active или Pending.

Кнопки: рейтинг; получить задание либо моё задание и пропустить. Во время ожидания показывается точное оставшееся время. Показ уже активного задания не изменяет состояние и не выдаёт другое.

## 5. Пропуск и ответ

Пропуск: вопрос Да/Нет. Нет — без изменений. Да — завершает попытку как Skipped, возвращает задание прямо в хвост очереди, запускает N1. Проверяется актуальность attempt ID. Повторное Да ничего не возвращает повторно.

Ответ MVP: одна фотография или один фотоальбом, необязательная подпись. Текст, видео, документы и отдельные разрозненные сообщения не объединяются в один ответ. Фотоальбом собирается по media_group_id. После получения полного кандидата бот делает reply и предлагает Подтвердить/Заменить. Default: debounce альбома с продлением по каждой части; подтверждение доступно после завершения окна. Пограничные поздние части не прикреплять молча к уже подтверждённому ответу; обработать как устаревшее сообщение и объяснить пользователю.

Новый фотоответ до подтверждения заменяет кандидата; старые кнопки недействительны. Заменить очищает кандидата и оставляет активное задание. Пропуск возможен и при наличии кандидата.

Подтвердить: фиксирует snapshot задания, баллов, подписи, Telegram media references; создаёт Pending; попытка становится Submitted; Active освобождается; запускается N2 с серверного UTC времени успешного подтверждения. Следующее задание доступно после N2, апрув ждать не нужно. Ответ после подтверждения нельзя заменить. Фото, пришедшие без Active, не создают заявки.

После закрытия приёма старые подтверждения, включая фото, присланные ранее, не принимаются. Соревнующиеся закрытие и подтверждение имеют один атомарно определённый порядок. Фото, дошедшее до сервера после закрытия, не даёт права отправить ответ задним числом.

## 6. Модерация

На рабочей доске — фото/альбом и отдельная карточка с submission ID, именем/номером участника, текстом задания, баллами, временем ответа и кнопками Approve/Reject. Никаких реакций как управляющих команд.

Approve: первый разрешённый организатор фиксирует решение, получает запись начисления. Repeatable возвращается в ПУЛ СВОЕГО БАКЕТА, не прямо в очередь. Одноразовое больше не доступно. Затем обычное пополнение очереди.

Reject: решение сохраняется; задание независимо от Repeatable возвращается прямо в хвост очереди; баллов нет. Default: обязательная причина из короткого списка, отклонение вступает в силу только после выбора причины. До этого заявку может проверить другой организатор; первое финальное решение побеждает. Отмена выбора причины не меняет Pending.

Участник получает результат, баллы/причину. N2 не перезапускается от решения. Принятые решения неизменяемы в MVP; исправление ошибочного решения требует отдельного согласованного сценария.

После успешного архивирования рабочие фото и карточка удаляются. Ошибка удаления не отменяет решение; резервный вариант — убрать кнопки и отметить исход. Оперативный чат предназначен для необработанных заявок, журнал туда не публикуется.

## 7. Архив

Все подтверждённые ответы, включая будущие Reject/Unreviewed, копируются без скачивания в приватный Telegram-архив. Альбом сохраняется. Карточка содержит стабильный submission ID, автора, задание, баллы, SubmittedAt и итог модерации. На фото и карточку сохраняются Telegram IDs. В пользовательском сообщении перед первой отправкой указать, что фото видят организаторы и сохраняют для просмотра после вечеринки.

Архивировать как можно раньше после подтверждения. Источником для рабочей копии желательно использовать уже созданный архив. Успешное архивирование — необходимое условие удаления рабочей копии, но не условие записи ответа в БД. Сетевые ошибки повторяются, видны суперадмину. Архив Telegram — выбранное место хранения, не обещание бессрочного внешнего бэкапа.

## 8. Рейтинг

Топ-10 плюс собственное место и результат. Сортировка: сумма действующих одобренных наград DESC; время последнего одобренного ответа ASC. Последний = max(SubmittedAt) среди одобренных ответов, НЕ ApprovedAt. Отклонённые и Pending не участвуют. Для полного совпадения — стабильный Participant ID ASC. У нулевого результата нет квалифицирующего timestamp: после остальных равных использовать Participant ID.

После Finished показывать снимок, а не заново пересчитываемую таблицу. Границу top-10 применять после полного порядка сортировки.

## 9. Дисквалификация

Только из личной панели суперадмина: выбрать участника по номеру/имени, подтвердить, указать причину. Исключает из рейтинга и запрещает выдачу/пропуск/отправку. История и начисления не стираются. Default: Pending остаются проверяемыми, начисления сохраняются, но не дают места дисквалифицированному; это позволяет восстановить без потери результата. Восстановление возвращает прежний прогресс, не обнуляет кулдаун и не перестраивает очередь. Решение и причина аудируются.

## 10. Аудит

В БД: регистрация, имя, выдача, пропуск, подтверждение, решения, начисления, возвраты, дисквалификация/восстановление, переходы игры/форс-финал. Поля: EventId, UTC, ActorId/system, ParticipantId, связанные Task/Attempt/Submission ID, действие, данные/причина. Отдельная Telegram-проекция журнала для организаторов. Её сбой не ломает бизнес-операцию.

Технические логи отдельно: сетевые ошибки, retries, исключения. Не логировать токен, бинарные фото и полный входящий payload без необходимости.
