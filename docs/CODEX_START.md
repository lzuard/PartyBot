# Первое поручение Codex

Скопировать следующий текст в новый рабочий чат, открытый на корне репозитория:

> Реализуем Telegram-бота по Markdown-документам в этом репозитории. Прочитай AGENTS.md и все спецификации, включая QUEUE.md и DECISIONS.md. Требования в файлах — рабочий источник истины; обсуждение из другого чата тебе не требуется.
>
> Сейчас выполни этап 1 из TASKS.md: создай минимальный запускаемый .NET-проект, конфигурацию, persistence bootstrap и тестовую инфраструктуру. Используй defaults из DECISIONS.md, не блокируй работу вопросами о токенах или содержимом каталога: для разработки нужны placeholders, реальные секреты я заполню отдельно. Не реализуй остальные этапы одним гигантским изменением.
>
> Перед изменениями коротко назови обнаруженные реальные противоречия; если их нет, сразу приступай. Обычные технические решения принимай сам, но бизнес-логику не меняй. После выполнения запусти подходящие проверки, обнови TASKS.md и README реальными командами. В ответе перечисли результат, проведённые проверки и следующий этап. Не коммить секреты и не отправляй сообщения реальным пользователям.

## Следующие поручения

«Выполни этап 2 из TASKS.md целиком; QUEUE.md нормативен. Проверь все относящиеся к очереди сценарии ACCEPTANCE.md. Не меняй правила для упрощения реализации».

После каждого этапа просмотреть diff и результат проверок, затем сделать отдельный git commit. Документы передавать как файлы в репозитории, а не как огромную повторяющуюся вставку в каждый чат.

## Совместная работа двух чатов/агентов

- Один пишет код, второй делает review и обсуждает требования. Общая память — git и актуальные .md, не содержимое чатов.
- Для review указывать commit/branch или конкретный diff, чтобы обсуждалась одна версия.
- В одной рабочей директории не поручать двум агентам одновременную правку одинаковых файлов. Для независимых правок использовать отдельные ветки/worktrees.
- Результат review: конкретный сценарий бага, файл/место, последствия, предложенное исправление и необходимая проверка.
- Изменение требований сначала отражается в SPEC/QUEUE/STATES/DECISIONS, затем в коде и ACCEPTANCE. Не сохранять противоречащие старые правила рядом с новыми.
