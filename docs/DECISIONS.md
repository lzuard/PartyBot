# Решения и допущения

Дата исходной версии: 2026-10-18. Новые решения добавлять с датой и причиной, устаревшие явно помечать superseded. Не трактовать молчание как отдельное согласование каждого default.

## Явно согласовано владельцем

- После отправки ответа можно продолжать задания, не дожидаясь апрува.
- Фотоответ подтверждается кнопкой; модерация кнопками.
- Баллы произвольные, default 1; бакеты автоматически по ценности.
- Очередь содержит целевые 5 невзятых; прямые возвраты обходят лимит/бакеты, но учитываются в длине и не двигают выбор бакета.
- Repeatable Approved возвращается в ПУЛ соответствующего бакета, не прямо в Queue. Это последнее исправление имеет приоритет над старым обсуждением.
- Реджект возвращает задание в невзятые; история попытки сохраняется.
- Два уровня админства, суперадмин один; DQ и state-кнопки в его личном чате.
- Закрытие приёма отдельно от закрытия модерации; при Pending обычный финал запрещён, нужен force override.
- Ничья по времени последнего ответа, который одобрен и участвует в результате, не по времени апрува; раньше лучше.
- Рабочий чат очищается после решения; фото сохраняются в отдельном Telegram-архиве.
- Нужен просматриваемый бизнес-журнал.

## Явные defaults для реализации

Это необходимые детализации, предложенные при подготовке комплекта. Реализовывать их последовательно; изменение владельцем обновляет спецификацию и проверки.

| Деталь | Default |
| --- | --- |
| Обход бакетов | Цикл по возрастанию стоимости, не исчерпание всего дешёвого бакета |
| Cursor после пустых бакетов | Следующий после фактически выбранного |
| Момент пополнения | Сразу после GetTask и иных изменяющих доступность операций |
| Возврат в пул | В хвост персонального пула своего бакета |
| Skip/Reject | Сразу в хвост Queue, потом Refill |
| Что считать временем ответа | Серверное время успешного ConfirmSubmission |
| ForceFinalize | Pending→Unreviewed, без баллов |
| Причина Reject | Обязательный короткий список |
| Каталог после Open | Заморожен |
| DQ Pending | Можно проверить, но участник исключён из рейтинга |
| Reinstate | Сохраняет прогресс, начисления и кулдаун |
| После Finished | Нет изменения рейтинга или DQ, только чтение |
| Ошибочный апрув | Нет отмены в MVP; отдельный сценарий нужен, если владелец запросит |
| Имена | 1–40 символов, совпадения с коротким номером |
| Фотоформат | Одна фотография или фотоальбом, подпись по желанию |
| Архив | Все подтверждённые ответы, не только одобренные |
| Стек | .NET 10 + EF Core 10 + SQLite, long polling, один процесс |

В примере пользователя 20 заданий×1, 5×2, 1×6 упоминание третьего бакета «3» трактуется как опечатка. Бакеты вычисляются из реальных Points: 1,2,6, без ручного маппинга 6→3.

## Параметры, которые владелец заполняет до запуска

- N1/N2: production-значений нет; development placeholders 1/1 минута.
- Каталог заданий, тексты монстра, причины реджекта.
- Telegram токен, числовые ID ролей/чатов, постоянное хранилище БД.
- Название игры и условия вручения призов.

## Осознанные ограничения

- Поздняя регистрация даёт меньше времени на очки; отдельного выравнивания времени нет.
- Пропуски/реджекты, возвращаемые напрямую, могут менять баланс бакетов; это требование.
- Постоянный cooldown и возвращаемые задания не гарантируют отсутствие фарма простых repeatable. Дополнительные лимиты агент не вводит самостоятельно.
- ForceFinalize может изменить потенциального победителя из-за непроверенных ответов; перед подтверждением показывается количество.
- Telegram — единственное медиа-хранилище; приложение не обещает независимую резервную копию фото.

## Технические решения этапа 1 — 2026-10-18

- Существующий `PartyBot.Api` преобразован из Web API в Generic Host; имя и путь сохранены, тесты в `PartyBot.Tests`. Это техническое отклонение от примерных путей `src/HalloweenBot` в ARCHITECTURE, без изменения границ компонентов.
- Этап 1 не регистрирует сетевой Telegram gateway и не запускает polling. Пустой токен/нулевые ID — placeholders; они допустимы для Development. Вне Development настройки ролей, поверхностей, абсолютного пути БД и явных N1/N2 проверяются до миграции. Проверки каталога и Telegram-доступа перед Open появятся с соответствующими сценариями.
- Миграции применяются при старте и командой `--migrate-only`. Начальная таблица Bootstrap — только инфраструктурная отметка, не состояние игры. Бизнес-таблицы добавляются по этапам.
- SQLite: FK включены, busy timeout 30 секунд, UTC timestamps представлены INTEGER ticks для корректного SQL-сравнения/сортировки. Один процесс; WAL специально не включается.
- Относительные пути конфигурации разрешаются от каталога исполняемого приложения (включая publish). Для production обязателен абсолютный постоянный путь БД.
- Каталог `Content/catalog.demo.json` явно демонстрационный, на этапе 1 не импортируется в БД. N1/N2 = 1/1 заданы только в appsettings.Development.json.
- Сигнатура `ITelegramBotClient.SendMessage` проверяется компиляцией адаптера с закреплённым Telegram.Bot 22.10.3.3 и XML-документацией установленного пакета; исходники SDK: https://github.com/TelegramBots/Telegram.Bot .
- Зависимости Microsoft.Extensions.Hosting, EF Core и dotnet-ef закреплены на 10.0.13 после предупреждений NuGet об уязвимостях транзитивных зависимостей версии 10.0.0. FakeTimeProvider использует доступный пакет Microsoft.Extensions.TimeProvider.Testing 10.1.0.
