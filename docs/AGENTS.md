# Инструкции Codex

## Задача

Реализовать небольшой надёжный Telegram-бот для одной Halloween-вечеринки. Сначала прочитай README.md, SPEC.md, QUEUE.md, STATES.md, DECISIONS.md, ARCHITECTURE.md, ACCEPTANCE.md и TASKS.md. Соблюдай требования, а не пересказывай их вместо реализации.

## Работа

- Выполняй один законченный этап TASKS.md за раз. Не останавливайся на плане, если поручена реализация.
- Самостоятельно принимай обратимые технические решения в рамках документов. Не спрашивай разрешения на обычные правки и проверки.
- Не добавляй бизнес-правила, экраны, состояния и фичи без основания. Допущения фиксируй в DECISIONS.md, не выдавай их за согласованные требования.
- При реальном противоречии назови файлы, приведи входной сценарий и предложи конкретное решение. Независимую работу продолжай.
- Сохраняй существующие изменения пользователя. Не делай destructive reset, force push, удаления БД или production-сброса игры без явного поручения.
- Не коммить секреты, БД, фото и production-логи. Не отправляй сообщения реальным участникам при тестировании.
- Не запускай одновременно production и локальный polling с одним токеном.
- В конце этапа: что изменено, что проверено, ограничения, следующий этап. Обнови TASKS.md; README — только реальными командами, когда код существует.
- Не заявляй об успешном тесте без запуска. Если запуск невозможен, укажи конкретную причину.

## Техника

- Default: C# / .NET 10, EF Core 10, SQLite, Telegram.Bot, long polling, один экземпляр.
- Один основной проект и один проект xUnit-тестов. Папки по ответственности; без обязательных CQRS/MediatR, generic repositories, брокеров, Redis и микросервисов.
- Telegram — адаптер. Правила очереди, проверок и рейтинга тестируются без Telegram API.
- Используй TimeProvider и внедряемый источник случайности. Кулдауны хранятся как UTC timestamps.
- Не держи транзакцию БД во время сетевого вызова. Действия БД и внешняя доставка разделены.
- Для надёжной доставки — простая персистентная очередь исходящих действий. Не обещай exactly-once доставку Telegram.
- Начисление баллов, решение модератора и возврат задания выполняются одной транзакцией.
- События одного участника сериализуются; идемпотентность и уникальные ограничения защищают от повторов.
- Каждая callback-кнопка проверяет actor, game state и актуальную attempt/submission/candidate/version, а не только текст callback.
- Авторизация по Telegram ID, не username и не членству в чате.
- Суммы баллов и tie-break вычисляются по действующим одобренным ответам. Храним историю решений.
- Проверь актуальные сигнатуры установленного Telegram SDK по официальной документации/исходникам. Не подменяй Bot API клиентским MTProto API.

## Проверки

Для бизнес-логики обязательны сценарии ACCEPTANCE.md, включая очереди, конкурентный апрув, рестарт, форс-финал. Проверки EF/SQLite проводить на реальном SQLite, не только EF InMemory. Не писать тесты на тривиальные getters и тексты реплик. Ручные Telegram-проверки выполнять только отдельным тестовым ботом.
