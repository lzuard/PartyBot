# PartyBot

Telegram-бот одной Halloween-вечеринки. Реализованы этапы 1–6: .NET 10 Generic Host,
SQLite, регистрация, персональные пулы/очередь, выдача заданий, подтверждаемый пропуск
и кулдаун, фотоответы/альбомы, архив, модерация и начисление баллов.
Добавлены рейтинг, личная панель суперадмина, DQ/восстановление и бизнес-журнал.
Добавлены закрытие приёма, обычный/форсированный финал и неизменяемый итоговый рейтинг.
Добавлены диагностика и восстановление доставок, backup/restore и deployment-шаблон.
Следующий этап — ручная репетиция отдельным тестовым ботом.
Спецификации: [docs/README.md](docs/README.md), прогресс: [docs/TASKS.md](docs/TASKS.md).

## Сборка и безопасный локальный запуск

Нужен .NET SDK 10.0.400 или более новый patch этой feature band. Из корня репозитория:

```sh
dotnet restore PartyBot.slnx
dotnet tool restore
dotnet build PartyBot.slnx --no-restore
dotnet test PartyBot.slnx --no-build
dotnet run --project PartyBot.Api --launch-profile Bootstrap
```

По умолчанию `Bot:PollingEnabled=false`: запросов к Telegram нет, токен не нужен.
Приложение применяет миграции, при первом обычном запуске импортирует демонстрационный
каталог, создаёт игру в Registration и ждёт Ctrl+C. Перезапуск сохраняет данные.
Профиль Bootstrap задаёт `DOTNET_ENVIRONMENT=Development`.

Только миграции, без импорта каталога, polling и ожидания Ctrl+C:

```sh
dotnet run --project PartyBot.Api --launch-profile Bootstrap -- --migrate-only
dotnet ef migrations list --project PartyBot.Api
dotnet ef migrations has-pending-model-changes --project PartyBot.Api
```

Для отдельной БД можно переопределить путь:

```sh
dotnet run --project PartyBot.Api --launch-profile Bootstrap -- --migrate-only --Bot:DatabasePath=/tmp/partybot-stage6-check.db
```

Миграции `GameQueueRegistration`, `PhotoAnswers`, `RankingPanelsAudit` и
`GameFinalization` и `DeliveryRecovery` обновляют БД этапов 1–5 без удаления прежних данных.
При обычном запуске файл `DATABASE.db.lock` предотвращает второй процесс на той же
БД; после остановки файл может оставаться, блокировка освобождается. EF CLI не
использует эту блокировку: миграции вручную выполняйте при остановленном приложении.

## Подключение отдельного тестового Telegram-бота

Это инструкция для ручной репетиции; при разработке реальные сообщения не отправлялись.
Для polling и `/open` заполните:

- `Bot:BotToken` — токен отдельного тестового бота;
- `Bot:SuperAdminUserId` — ваш Telegram user ID; `Bot:OrganizerUserIds` — ID организаторов;
- `Bot:ModerationChatId`, `Bot:ArchiveChatId`, `Bot:AuditChatId` — разные отдельные тестовые чаты;
- `Bot:DatabasePath` — абсолютный путь к отдельной постоянной тестовой БД;
- N1/N2 — в Development доступны явно помеченные defaults 1/1 минута.

Секреты храните в .NET user-secrets проекта или переменных окружения. Например,
ключ `Bot:BotToken` в user-secrets соответствует переменной `Bot__BotToken`.
Не записывайте токен в отслеживаемые JSON-файлы или аргументы запуска.

После настройки включение polling выполняется явно:

```sh
dotnet run --project PartyBot.Api --launch-profile Bootstrap -- --Bot:PollingEnabled=true
```

Не запускайте другой polling с тем же токеном даже на другой БД. Бот не удаляет
webhook и не сбрасывает ожидающие updates. Ошибки Telegram 401/409 останавливают
polling; нужно исправить конфигурацию или конфликт экземпляров.

В личном чате тестового бота:

1. `/start` → `/name Ваше имя`. Совпадающие имена различаются номером `#Id`.
2. Суперадмин отправляет `/open` и нажимает «Да». До подтверждения выдача закрыта.
3. `/task` или «Получить задание» выдаёт голову персональной очереди.
4. `/mytask` показывает текущую попытку без новой выдачи.
5. `/skip` или «Пропустить» → «Да» возвращает задание в хвост и запускает N1;
   «Нет» сохраняет попытку. До границы кулдауна бот показывает оставшиеся секунды.
6. При активном задании отправьте одно фото или альбом только из фото. После паузы
   сборки (default 2 секунды) нажмите «Подтвердить» либо «Заменить». Замена требует
   нового сообщения/альбома. Старые кнопки и поздние части прежнего альбома отклоняются.
7. Подтверждение сохраняет ответ и запускает N2; после N2 можно взять следующее
   задание, не дожидаясь проверки. Фото доступны организаторам и сохраняются в архиве.
8. В рабочем чате организатор нажимает Approve либо Reject → причину. Первое решение
   окончательное; повторные нажатия не начисляют баллы снова. Reject возвращает
   задание в очередь без повторного запуска N2. Approve возвращает repeatable в пул.
9. `/name Новое имя` меняет имя с аудитом, сохраняя очередь и историю.

Callback-команды проверяют actor, ожидаемый чат, состояние игры и актуальность
попытки/версии. Старые кнопки не выполняют повторный возврат. Доступность действий
проверяется в application, а не только в клавиатуре.
Закрытие приёма и финал выполняются из личной панели суперадмина; обратного перехода
игры нет. Для новой независимой тестовой игры выбирайте новую БД.

## Рейтинг, панель и журнал

- `/rank` или кнопка «Рейтинг»: топ-10 и собственное место из одного полного порядка.
  Суммируются snapshot-награды Approved; ничья решается по max(SubmittedAt) Approved,
  затем по стабильному номеру. Время модерации не влияет. DQ исключены; нулевые
  результаты упорядочены по номеру. Просмотр не меняет очередь или кулдаун.
- `/admin` в личном чате суперадмина: состояние игры, страницы участников по 10,
  выбор по имени/номеру, рейтинг и открытие Registration-игры с подтверждением.
- Карточка участника показывает команду `/dq НОМЕР ПРИЧИНА` либо
  `/reinstate НОМЕР ПРИЧИНА`. Причина обязательна (1–300 символов), затем «Да/Нет».
  Подтверждение сохраняется в БД и проверяет текущую версию участника и игры.
  Если участник успел изменить прогресс, откройте карточку и повторите запрос.
- DQ запрещает игровые действия и исключает из рейтинга. Active, кандидат, очередь,
  баллы и кулдаун сохраняются; Pending можно проверять. Восстановление возвращает
  прежний прогресс. После Finished изменение DQ запрещено.
- Бизнес-журнал доставляется в `AuditChatId`, при заданном `AuditThreadId` — в тему.
  Он содержит EventId, время, actor, действие, идентификаторы связанных сущностей
  и данные/причину. Существующие события этапов 2–3 также проецируются после запуска.
  Сбой журнала не откатывает бизнес-операции; временные ошибки повторяются,
  постоянные сохраняются, суперадмин получает уведомление. Дубль сетевой отправки
  возможен; его можно узнать по EventId. Рабочий чат модерации журнал не получает.

## Закрытие приёма и финал

Все действия — только суперадмином в личном чате, через `/admin` либо команды:

1. `/close` → «Да»: Open → Review. Регистрация, выдача, пропуск и отправка ответов
   закрываются, включая старые кнопки подтверждения фото. Active и кандидаты остаются
   в истории; Pending продолжают проверяться. Закрытие не запускается по часам.
2. `/finalize` → «Да»: при нуле Pending сохраняется итог и игра переходит в Finished.
   Если Pending есть, обычный финал запрещён.
3. `/forcefinalize ПРИЧИНА` → отдельная кнопка «Подтвердить форс-финал».
   Предупреждение показывает число Pending и последствия для результата. Причина
   обязательна (1–300 символов). Если число Pending изменилось после вопроса,
   повторите команду и подтвердите актуальное число. «Нет» отменяет запрос.

Форс-финал переводит остаток в Unreviewed: без баллов, возврата в очередь/пул и
изменения кулдауна. Это не Reject. Участник получает объяснение; архив обновляется,
рабочая копия очищается после полного архивирования. Доставка продолжается и после
Finished, её сбой не отменяет финал.

Состояние, результаты, причина/факт форса, время и actor сохраняются одной транзакцией.
Подтверждения переживают рестарт, проверяют версию игры и используются однократно.
После Finished `/rank` читает snapshot имён, очков, мест, tie-break и DQ, включая
собственное место вне топ-10. Изменения участника, модерация и DQ закрыты. Штатного
исправления итогов/обратного перехода в MVP нет. Не меняйте состояние игры вручную.

## Конфигурация и каталог

Приоритет: `appsettings.json` → `appsettings.{Environment}.json` → user-secrets
(Development) → environment → аргументы командной строки. Относительные пути
разрешаются от каталога исполняемого приложения; Debug-БД по умолчанию:
`PartyBot.Api/bin/Debug/net10.0/data/partybot.db`.

Остальные настройки:

- `Bot__OrganizerUserIds__0`, `Bot__OrganizerUserIds__1`: элементы списка ID;
- `Bot__AuditThreadId`: необязательная тема журнала;
- `Bot__SkipCooldownMinutes`, `Bot__SubmitCooldownMinutes`: N1/N2, явно задать вне Development;
- `Bot__CatalogPath`: JSON-каталог; default `Content/catalog.demo.json`;
- `Bot__DisplayTimeZone`: Europe/Moscow; все timestamps в БД — INTEGER UTC ticks;
- `Bot__AlbumDebounceSeconds`: default 2, допустимо 1–30;
- `Bot__RejectReasons__condition`, `__unclear`, `__wrongtask`: тексты короткого списка
  причин (ключи полного пути: например `Bot__RejectReasons__unclear`). Defaults —
  разработческие placeholders; согласуйте тексты перед игрой.

Каталог содержит `demonstrationOnly` и `tasks`: `stableId`, `text`, `points`
(положительное целое, default 1), `repeatable`. ID уникальны. Каталог импортируется
только при создании игры, затем источником служат таблицы БД: редактирование JSON
не меняет существующую игру, награды или персональные пулы. Отдельный редактор/
повторный импорт для существующей Registration-игры в этот этап не входит.
Подготовьте каталог до первого запуска целевой БД. После Open он заморожен.
Демонстрационный каталог допускается только для Development-открытия;
production `/open` его отклоняет.

Вне Development, а также при включении polling и при `/open`, проверяются токен,
ID, разные поверхности, явные N1/N2 и абсолютный путь БД. Это проверка конфигурации,
не Telegram-прав на отправку/редактирование/удаление: права и полную доставку фото
нужно будет проверить перед реальной игрой по [OPERATIONS](docs/OPERATIONS.md).

## Надёжность и тесты

Один основной проект `PartyBot.Api` (историческое имя, HTTP-сервера нет) и один
`PartyBot.Tests`. Domain не зависит от Telegram. TimeProvider и IRandomSource
заменяются в тестах; интеграционные тесты используют файловую SQLite и fake gateway.

Входящие команды сериализуются общим gate. Изменения игры, аудит, ProcessedUpdate,
offset и исходящие действия фиксируются одной транзакцией. Явный getUpdates
читает сохранённый offset. Отдельный worker отправляет ответы без транзакции БД
на время запроса, повторяет временные ошибки, учитывает retry_after и отмечает
постоянные ошибки; блокировка бота одним пользователем не задерживает остальных.
При сбое между отправкой Telegram и сохранением message ID возможен дубль доставки.
Фото сохраняются в Telegram по file_id без скачивания; архив содержит снимок задания,
награды, автора, подписей и итогового решения. Рабочая копия берётся из архива,
при отказе копирования используется file_id. Частичная доставка не считается полным
архивом. Рабочие сообщения удаляются только после полного архива; перед удалением
карточка обновляется итогом без кнопок. Ошибка доставки/удаления не отменяет решение.
Первая ошибка и постоянный отказ уведомляют суперадмина; состояние остаётся в БД.
Постоянные ошибки восстанавливаются суперадмином через `/retry НОМЕР` с подтверждением.
Успешные доставки и временный retry_after вручную не сбрасываются.
Медиа-шаг сериализован с командами для актуальности кнопок и ограничен 15 секундами;
сетевой вызов не держит транзакцию БД, но может на это время задержать входящую команду.

120 .NET-тестов покрывают QUEUE.md, фото/альбомы, подтверждение, модерацию и начисления,
повторный /start, имена, роли, старые callback, N1, конкуренцию, откат транзакции,
рестарт, миграции с нуля/этапов 1–5, частичные альбомы, retry_after и ошибки cleanup.
Также проверены tie-break/top-10, DQ/восстановление, роли панели, откат транзакции
DQ, сохранение истории и независимая доставка журнала с темой.
Этап 5 добавляет закрытие приёма, оба финала, Unreviewed, snapshot/top-10/нулевые
результаты, гонки Confirm/Close и Approve/ForceFinalize, отмену/старые кнопки,
атомарный откат и чтение неизменяемого итога после рестарта.
Этап 6 проверяет host restart/offset, восстановление Failed, повторный отказ,
продолжение частичного cleanup, роли диагностики и отсутствие изменений баллов/финала. `Telegram.Bot` закреплён на
22.10.3.3; сигнатуры сверены с XML-документацией установленного пакета.

## Эксплуатация

В личной панели суперадмина: `/diagnostics` показывает состояние игры, Pending,
неполный архив, собираемые альбомы, незавершённые/Failed доставки, ошибки доски/cleanup
и offset. После исправления прав используйте `/retry НОМЕР` → «Повторить».
Это повтор доставки, без повторного Approve и начисления. Доступно и после Finished.
Временные ошибки повторяются автоматически; успешные действия не переотправляются.

[OPERATIONS.md](docs/OPERATIONS.md) содержит настройку `deploy/compose.yaml`, запуск,
остановку, обработку 401/409, ограничения Telegram, backup/restore и репетицию.
Секреты для Compose хранятся в gitignored `deploy/partybot.env`; пример с placeholders
— `deploy/partybot.env.example`, polling по умолчанию выключен.

SQLite-aware утилита (Python 3, только стандартная библиотека):

```sh
python3 scripts/sqlite_backup.py backup /tmp/partybot-stage6-check.db /tmp/partybot-stage6-backup.db
python3 scripts/sqlite_backup.py verify /tmp/partybot-stage6-backup.db
python3 scripts/sqlite_backup.py restore /tmp/partybot-stage6-backup.db /tmp/partybot-stage6-restored.db
python3 -m unittest discover -s scripts -p 'test_*.py' -v
docker compose -f deploy/compose.yaml config --no-env-resolution --no-interpolate -q
```

Destination всегда должен быть новым файлом; существующая БД не перезаписывается.
Проверены 3 Python-теста (включая online WAL backup), реальная копия тестовой БД,
восстановление и запуск Release-публикации без polling. Восстановление старой копии
может потерять более поздние данные; Telegram не обязан повторно выдать уже подтверждённые updates.

Секреты, БД, фото и логи исключены из Git/Docker context. Compose проверен CLI;
Docker daemon недоступен, поэтому Docker build/run не проверены. Ручная Telegram-репетиция
не выполнялась. Пользовательский `PartyBot.Api.http` сохранён;
его шаблонные HTTP-запросы неприменимы к Generic Host.
